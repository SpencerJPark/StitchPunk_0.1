# Player Resource System + Summon Cost — Design Spec

> **Status:** ✅ spec ready (rewritten 2026-09-15 after `Code_Audit_2026-09.md`; the 2026-07 draft's six open decisions are settled below as PR-D1–PR-D12, and the scope grew by one step: **revival costs resources**). Three ← DECISION markers remain, all HUD presentation, all the owner's. Build plan is §12.
> **Raw source:** [`futureneedsplan.md`](futureneedsplan.md) → "Player resource system"; `Spencer/Design_Decisions.md` → RTS Mode ("the base unit is 1 body, some electricity, and some mechanical scrap. electricity is generated by burning wood … the only cap is available body resources").

## Context

The game has no economy. Revival is free (`PlayerReviverSystem` enables `ReviveRequest` and nothing is checked), corpses are not a resource, and the old `ResourceManager` / `ResourceTypeSO` / `ResourceManagerUI` are all commented out. `UnitSO.cs:57–60` still carries the commented `spawnCostResourceAmountArray` from that era. The owner's design answer names the rule the game runs on: a base unit is one body plus electricity plus scrap, wood burns into electricity, and the only unit cap is bodies. Nothing implements it.

This spec builds the ledger the 2026-07 draft described **and the first real spender**: raising a corpse in the field costs the undead form's authored scrap and electricity (the body is the corpse under the reviver). Every later spender (caravan summoning, building placement, trade) and producer (factory, harvesting, corpse collection) goes through the same two buffers.

Patterns reused, all live: the `Player` singleton tag, `MotivationChangeRequest` + `MotivationChangeRequestSystem` (delta buffer, consumer clears), `IPersist` on a blittable component, `MinionGroupHUD` + `RiveUtils` (ECS→Rive read-only bridge), `UnitSO` → `UnitDataBlob` through `UnitLibraryBakingSystem`.

**Skills Needed:** `dots-system-scaffold` (§5 systems), `dots-authoring-baker` (§7 player bake), `dots-test` (§9 fixtures). No `dots-blob-library`: the cost rides the existing unit library, no new library.

## 1. Purpose & v1 scope

A per-player resource ledger on the `Player` entity, mutated only through a delta buffer, persisted via the save system, spent by revival, shown on a HUD.

**v1 handles:**
- `ResourceType` enum and the five starter resources (PR-D1).
- `ResourceStack` ledger buffer on `Player`, one entry per resource, baked at zero (PR-D5).
- `ResourceChangeRequest` delta buffer as the only mutation path; `ResourceChangeSystem` applies and clears it.
- `StorageCapacity` per-resource cap; missing entry = uncapped.
- `ResourceLedger` static helpers: `Get`, `CanAfford`, `TrySpend`.
- `SummonCost` authored per `UnitSO`, baked into `UnitDataBlob.summonCost`; `PlayerReviverSystem` charges it before enabling `ReviveRequest` and stamps `ResourceShortfall` when it cannot.
- `PlayerResourcesSnapshot : IPersist` save round-trip through two sync systems.
- `ResourceHudManager` (Rive) showing the five counts and flashing a shortfall.
- `DebugResourceMenu` (OnGUI, mirrors `DebugZombifyMenu`) to add or spend each resource for verification.

**Out of v1 (reserved, do not build):** wood → electricity burning (a workstation/caravan system, PR-D10); corpse collection into the ledger (PR-D11); caravan summoning that also charges `corpses`; factory/harvest producers; trade currency; icons/prices library; atomic multi-frame spend reservation.

## 2. Architecture

Pure ECS data + mutation, plus a read-only MonoBehaviour bridge. Nothing crosses back from the HUD.

```
spenders: PlayerReviverSystem (PlayerEquipmentSystemGroup)         producers: DebugResourceMenu now; factory/harvest later
        └─ ResourceLedger.TrySpend → appends negative ResourceChangeRequest, or stamps ResourceShortfall
PlayerResourceSystemGroup   (Simulation: after BuildingsSystemGroup, before CombatSystemGroup)
        └─ ResourceChangeSystem: apply deltas → ResourceStack clamped [0, cap] → requests.Clear()
HealthSystemGroup
        └─ ReviveRequestSystem: unchanged, consumes the ReviveRequest the reviver enabled
SaveSystemGroup (Late)
        ├─ ResourceSaveSyncSystem  (before PersistentSaveSystem): ResourceStack → PlayerResourcesSnapshot
        └─ ResourceLoadSyncSystem  (after  PersistentLoadSystem): PlayerResourcesSnapshot → ResourceStack
MonoBehaviour LateUpdate: ResourceHudManager reads ResourceStack + ResourceShortfall → Rive properties
```

**PR-D2 — group:** `PlayerResourceSystemGroup : GameSceneSystemGroup`, `[UpdateAfter(typeof(BuildingsSystemGroup))] [UpdateBefore(typeof(CombatSystemGroup))]`, declared in `SystemGroups.cs` and added to `SystemGroupOrderTests`' simulation list between `BuildingsSystemGroup` and `CombatSystemGroup`. Folder `Assets/_Scripts/Systems/PlayerResourceSystemGroup/`. Reason for the slot: producers in `BuildingsSystemGroup` and spenders in `PlayerSystemGroup` have both run; combat and health see settled numbers. The spend queued by the reviver in frame N is applied in frame N, after the revive was granted, which is correct because `TrySpend` already verified affordability against the live stack.

## 3. Entry points

| Contract | Kind | Producers | Consumer |
|---|---|---|---|
| `ResourceChangeRequest` | buffer on `Player` | `PlayerReviverSystem` (spend), `DebugResourceMenu`, later factory/harvest/trade | `PlayerResourceSystemGroup` — `ResourceChangeSystem` |
| `ResourceShortfall` | enableable component on `Player`, time-stamped | any `TrySpend` caller | `ResourceHudManager` (read-only; nobody clears it, PR-D8) |
| `ResourceLedger.Get / CanAfford / TrySpend` | static helpers | any Burst job or system with the two buffers | — |

No one-frame signal entity: the player pool is one well-known singleton, so buffers on it beat spawning entities.

## 4. Data model

**`Assets/_Scripts/Data/Enums/ResourceType.cs`** (PR-D1, PR-D3):
```csharp
public enum ResourceType { None, Wood, ScrapMetal, Corpse, Electricity, Currency }
public enum ResourceChangeType { Add, Set }
```
`Corpse` not `Body`: the code already says corpse everywhere (`CorpseCells`, `corpseStackOffset`). The HUD label is the owner's ("Bodies" is fine). A dedicated `ResourceChangeType` rather than reusing `MotivationChangeType`: the AI enum file must not become a dependency of player data.

**`Assets/_Scripts/Components/Player/ResourceComponents.cs`:**
```csharp
public struct ResourceStack : IBufferElementData { public ResourceType resourceType; public int amount; }
public struct StorageCapacity : IBufferElementData { public ResourceType resourceType; public int cap; }
public struct ResourceChangeRequest : IBufferElementData
{
    public ResourceType       resourceType;
    public ResourceChangeType changeType;   // Add: += value; Set: = value. Both clamp to [0, cap].
    public int                value;
}
// Stamped by any TrySpend that fails. Never cleared: the HUD compares stampedTime to the last it showed.
public struct ResourceShortfall : IComponentData, IEnableableComponent
{
    public ResourceType resourceType;   // the first resource that came up short
    public int          missing;
    public double       stampedTime;    // SystemAPI.Time.ElapsedTime at the failed spend
}
// Blittable mirror of ResourceStack for IPersist (buffers are not saveable in v1, PersistComponents.cs).
public struct PlayerResourcesSnapshot : IComponentData, IPersist
{
    public int wood, scrapMetal, corpse, electricity, currency;
}
```
**PR-D4** named ints, not a fixed array: five resources, and a layout change already breaks old saves for every `IPersist` struct (`BodyPartComponents.cs:52` records the same trade-off). **PR-D5** all five `ResourceStack` entries are baked at 0 and never pruned: stable indices, the HUD never misses a row, no structural change on first gain.

**Summon cost** — `Assets/_Scripts/Data/Structs/UnitBlob.cs` gains, and `UnitDataBlob` gets a field of:
```csharp
public struct SummonCostBlob { public int corpses; public int scrapMetal; public int electricity; }
```
`Assets/_Scripts/Data/SOs/UnitSO.cs` replaces the commented `[Header("Spawn Cost")]` block (lines 57–60) with:
```csharp
[Header("Summon Cost")]
[Tooltip("Charged when this unit is raised. In-field revival skips corpses (the corpse under the reviver is the body); caravan summoning charges all three.")]
public SummonCost summonCost = new SummonCost { corpses = 1, scrapMetal = 1, electricity = 1 };
```
with `[System.Serializable] public struct SummonCost { public int corpses; public int scrapMetal; public int electricity; }` in the same file. `UnitLibraryBakingSystem.cs:64–67` copies it next to `becomesUnitType` / `maxHealth`. **PR-D6:** the cost is authored on the **undead** form, the unit you are making, and looked up through `becomesUnitType` at revive time (`ReviveJob` already does this lookup at `ReviveRequestSystem.cs` for the animation keys). A living unit's own `summonCost` is ignored.

## 5. Systems

| System | Group | Reads | Writes |
|---|---|---|---|
| `ResourceChangeSystem` | `PlayerResourceSystemGroup` | `ResourceChangeRequest`, `StorageCapacity` | `ResourceStack` (clamp), clears requests |
| `PlayerReviverSystem` (edit) | `PlayerEquipmentSystemGroup` | `Target`, `UnitData` of target, `UnitDataLibrary`, `ResourceStack` | `ResourceChangeRequest`, `ResourceShortfall`, enables `ReviveRequest` |
| `ResourceSaveSyncSystem` | `SaveSystemGroup`, `[UpdateBefore(typeof(PersistentSaveSystem))]` | `ResourceStack` | `PlayerResourcesSnapshot` |
| `ResourceLoadSyncSystem` | `SaveSystemGroup`, `[UpdateAfter(typeof(PersistentLoadSystem))]` | `PlayerResourcesSnapshot` | `ResourceStack` |

All `ISystem`, `[BurstCompile]`, `state.RequireForUpdate<Player>()`. Group-level scene gating; no per-system `GameSceneTag`. The two sync systems mirror every frame (five ints, free) so no "did a save happen" signal is needed. `ResourceLoadSyncSystem` only writes when the snapshot differs from the stack, so it does not fight the save mirror. If that proves circular in the fixture, gate the load mirror on `PersistentLoadSystem`'s existing load-complete signal instead and record the change in §13.

**`ResourceChangeSystem`** is an `IJobEntity` over `Player` with `ref DynamicBuffer<ResourceStack>`, `ref DynamicBuffer<ResourceChangeRequest>`, `in DynamicBuffer<StorageCapacity>`, `.Schedule()` (one entity, never `.Run()`), body shaped exactly like `MotivationChangeJob`. Clamp: `Add` → `amount = clamp(amount + value, 0, cap)`; `Set` → `amount = clamp(value, 0, cap)`; cap from `StorageCapacity` or `int.MaxValue`.

**`PlayerReviverSystem`** edit, the only behavioural change in the spec. Today (`PlayerReviverSystem.cs:17–35`): if `OnPlayerReviverEquip` is enabled and `Target` is enabled and the target has `ReviveRequest`, enable it. New body between "target has `ReviveRequest`" and the enable:

```csharp
UnitType corpseUnitType  = unitDataLookup[targetEntity].unitType;
int      corpseIndex     = unitLibrary.Value.FindByUnitType(corpseUnitType);
UnitType becomesUnitType = corpseIndex >= 0 ? unitLibrary.Value.units[corpseIndex].becomesUnitType : UnitType.None;
int      undeadIndex     = becomesUnitType == UnitType.None ? -1 : unitLibrary.Value.FindByUnitType(becomesUnitType);
if (undeadIndex < 0) { /* not revivable — leave it to ReviveRequestSystem's existing no-op path */ }
else
{
    SummonCostBlob cost = unitLibrary.Value.units[undeadIndex].summonCost;
    bool affordable = ResourceLedger.TrySpend(ref resourceStack, ref resourceRequests, in cost,
        chargeCorpses: false, elapsedTime, ref shortfall, shortfallEnabled);
    if (!affordable) { reviverEnabled.ValueRW = false; continue; }
}
SystemAPI.SetComponentEnabled<ReviveRequest>(targetEntity, true);
```
The system stays main-thread `SystemAPI.Query` (it already is; one player, one input). **PR-D7:** the check lives in the spender, not in `ReviveRequestSystem`, because `SpawnStateInitSystem` also enables `ReviveRequest` (spawn-as-undead) and must stay free.

**`ResourceLedger`** (`Assets/_Scripts/Utils/ResourceLedger.cs`), static, Burst-friendly, no allocation:
```csharp
public static int  Get(in DynamicBuffer<ResourceStack> stack, ResourceType resourceType);           // 0 if absent
public static bool CanAfford(in DynamicBuffer<ResourceStack> stack, ResourceType resourceType, int amount);
// Checks every line of the cost first, then queues all negative Add deltas, or stamps the shortfall and queues nothing.
public static bool TrySpend(ref DynamicBuffer<ResourceStack> stack, ref DynamicBuffer<ResourceChangeRequest> requests,
    in SummonCostBlob cost, bool chargeCorpses, double elapsedTime,
    ref ResourceShortfall shortfall, EnabledRefRW<ResourceShortfall> shortfallEnabled);
```
`TrySpend` reads the **live** stack, not pending deltas: two spends in one frame could both pass. Accepted for v1 (one player input per frame); recorded as a Gotcha.

## 6. MonoBehaviour bridge (HUD)

`Assets/_Scripts/UI/ResourceHudManager.cs : MonoBehaviour`, shaped like `MinionGroupHUD` (plain MonoBehaviour, `RiveUtils.OnLoaded` → `RivePropertyCache`, cache last-pushed values, push only on change). Reads in `LateUpdate`. Rive artboard properties (numbers): `WoodCount`, `ScrapMetalCount`, `CorpseCount`, `ElectricityCount`, `CurrencyCount`, `ShortfallResource` (the `ResourceType` int, 0 = none), `ShortfallTick` (increments once per new `ResourceShortfall.stampedTime`; the artboard animates the flash off that change). The artboard itself is an owner art task, like the `MinionGroupHUD` one.

Until the artboard exists the manager also drives an optional `TMP_Text[] fallbackLabels` (five entries, index = `ResourceType - 1`) when assigned, so the verify pass does not wait on art. **PR-D9:** Rive is the game's chosen UI stack; TMP is the fallback, not a second HUD.

- ← DECISION (owner): HUD placement and reading order of the five counts, and whether `Corpse` is labelled "Bodies". Recommend a single row, top-left, Bodies first since it is the unit cap.
- ← DECISION (owner): on a failed revive, flash the short resource only, or also play a refusal sound through the existing sound system? Recommend flash only in v1; sound rides the next `SoundSystemGroup` content pass.
- ← DECISION (owner): starting ledger for `TestArea` / `Game` (`PlayerControllerAuthoring` exposes `startingResources`). Recommend `Wood 10, ScrapMetal 5, Corpse 0, Electricity 5, Currency 0` so exactly five field revivals are affordable at the default 1/1 cost.
