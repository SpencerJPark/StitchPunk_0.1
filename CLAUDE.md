## Environment & tooling

- **Engine:** Unity **6000.5.0f1** (Unity 6.5). Pinned in `ProjectSettings/ProjectVersion.txt`.
- **Stack:** Unity **DOTS** — Entities 6.5, Entities.Graphics, Physics 6.5, Burst, Collections, Mathematics, Jobs. Render: URP 17.5 (2.5D). Also: Cinemachine 3.1, Input System 1.19, UniTask (async), Reflex (DI), Rive (UI).
- **Unity MCP server** (`mcp__unity-mcp__*`) is the primary way to interact with the running Editor: `Unity_GetConsoleLogs` (read compile errors / Burst warnings / play-mode logs), `Unity_RunCommand`, `Unity_Camera_Capture` / `Unity_SceneView_Capture*` (screenshots). There is **no command-line build script** — compilation, baking, and play-testing happen inside the open Editor.

## Commands

This is an Editor-driven Unity project; there is no `make`/`npm`/`dotnet` build entry point for the game.

- **Compile / check for errors:** save the `.cs` file → Unity recompiles on focus. Read results with the Unity MCP `Unity_GetConsoleLogs` tool. Do **not** rely on the root `*.csproj` files — they are IDE-generated and regenerated by Unity.
- **Run / play-test:** enter Play mode in the Editor. Main scene `Assets/Scenes/Game.unity`; DOTS sandbox `Assets/Scenes/TestArea/DOTSTestScene.unity`.
- **Rebake subscenes:** changes to authoring/baking code or SO data require a re-bake — re-open the subscene or re-enter Play mode. A "compile + rebake + play" pass is the standard verification loop (several `_Vault` notes call this out explicitly).
- **Tests:** the project ships **no game-specific test assemblies** — only Unity package tests exist. Run those via **Window ▸ General ▸ Test Runner** (EditMode / PlayMode). There is no headless test command wired up.

## Architecture orientation

The codebase is one Unity project split into assemblies under `Assets/_Scripts/` (each has a `StitchPunk.*.asmdef`):

| Assembly | Holds | Rule of thumb |
|---|---|---|
| `Components/` | `IComponentData`, `IBufferElementData`, enums, tags | **Data only — no logic** |
| `Authoring/` | MonoBehaviour + nested `Baker` pairs; cross-entity baking systems | Wires prefabs/SOs → entities; no game logic |
| `Data/` | ScriptableObjects + their `BlobAsset` structs | SO → Blob pipeline (see below) |
| `Systems/` | `ISystem` + `IJobEntity` — all gameplay logic | Burst jobs; the bulk of the game |
| `MonoBehaviours/` | Managers, input, camera (non-ECS hybrid layer) | Bridges Unity-land ↔ ECS |
| `UI/`, `Core/`, `Utils/`, `Editor/` | UI, singletons/legacy, helpers, editor tooling | `Core/Unused/` = legacy parking, never referenced |

**Non-negotiable rules** (full list in `RULES.md`, reinforced by user memory):
- Never use `var`; never single-letter names — explicit types everywhere, names read like docs.
- Never `.Run()` a job — always `.Schedule()` or `.ScheduleParallel()`, assigned to `state.Dependency`.
- `[ReadOnly]` is imported from `Unity.Collections` (not `Unity.Entities`) — always add the using when used.
- Prefer `ISystem` (struct) + `[BurstCompile]` over `SystemBase`. No managed allocations inside Burst jobs.
- **SO → BlobAsset pattern:** runtime SO data is baked into a blob in `PostBakingSystemGroup`; systems read the blob via a singleton, never the SO. The repetitive five-file version of this is the `dots-blob-library` skill.

**System execution order** is centralized in [`Assets/_Scripts/Systems/SystemGroups.cs`](Assets/_Scripts/Systems/SystemGroups.cs) — always place a new system in the correct group via `[UpdateInGroup]` rather than ad-hoc ordering. The `SimulationSystemGroup` pipeline runs roughly:

`GameManager → Player (input → narrative → dialogue → equipment) → UtilityAI (motivation → awareness) → MinionActionSelection → StateMachine (selection → execution) → Item → Movement → Buildings → Combat → Health → Design → Animation`

then in `LateSimulationSystemGroup`: `Spawn → SpawnInit → Sound → Despawn → Save`.

**AI is a decision/execution split** (recent "Brain Control Split" architecture): awareness systems in `UtilityAISystemGroup` populate a `UtilityActions` buffer of scored options → the winner is written into the `StateMachine` component → a single `BehaviorExecutionSystem` interprets the chosen `BehaviorSO`'s blob-baked command sequence (Approach, RequestAttack, PlayAnimation, LoopUntil, …). See `Systems_AI.md` in the vault and the `dots-unit-ai` skill before touching AI.

## Project DOTS skills

Use the repo's scaffolding skills instead of hand-writing the boilerplate — they encode the conventions above and the bug-prone patterns:
`dots-system-scaffold` (new ISystem+job), `dots-authoring-baker` (MonoBehaviour+Baker), `dots-blob-library` (SO→Blob library pipeline), `dots-unit-ai` (awareness/action behaviours), `dots-task-creator` → `execute-plan` (plan then build a whole system). Canonical copies live in `.claude/skills/`; the index is `_Vault/Memories/Code/Skills.md`.
